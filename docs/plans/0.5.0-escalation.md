# 0.5.0 — Two-stage retrieval and the escalation record

**Contract 1.1.0** (no change) · Status: planned

## Goal

Make `no_match` the start of something instead of the end. Cheap deterministic
retrieval first; when it misses, escalate to whatever expensive thing the host
has — and **write the outcome back**, so the cheap layer is tuned by the
expensive one.

## Why now

`LIMITATIONS.md` concedes that keyword retrieval is the weakest component, and
`ANALYSIS-…` §4.3 goes further: a competent model reading twenty filenames beats
weighted scoring on any query the keyword author did not anticipate. Both are
true. Neither is a reason to add embeddings — it is a reason to make the miss
productive.

The insight this release is built on (`IDEAS.md` §2):

> When the cheap stage misses and the deep stage succeeds, that pair is a
> **labelled retrieval failure with the correct answer attached.**

That is a supervised training signal, produced for free, with an external
fixed point. Nothing else in this system generates one.

## Contract impact

None. The escalation record lives in the ledger, and the writeback uses existing
fields (`keywords`, `synonyms`) plus existing eval cases.

## Design

```
query
  │
  ├─→ searchMemory                       cost ~0, deterministic
  │      │
  │      ├─ match     → answer. done.
  │      └─ no_match  ─┐
  │                    │
  │      ┌─────────────┘
  │      ▼
  │   escalate(query)                    cost: real. host-provided.
  │      │                               (agentic filesystem read, web search,
  │      │                                vector index, another memory, a human)
  │      ▼
  │   result ─→ EscalationRecord ─→ writeback:
  │                                   • keywords on the atom that should have won
  │                                   • an eval case, so the miss is now a test
  │                                   • the gap, closed by that atom
  └─→ answer
```

### Sequential, not parallel

`IDEAS.md` proposed possibly running both at once. Rejected as the default:
parallel means always paying for the expensive path, which defeats the purpose of
having a cheap one. `parallel: true` exists as a flag for interactive surfaces
where 300 ms of latency costs more than the query does — and it is off by default
and documented as a latency/cost trade, not an accuracy one.

### The kit does not escalate

`escalate` is a host-provided function. This kit contains no model, no network,
and no search client, and 0.5.0 does not change that. What it provides is the
*protocol*: when to escalate, what to record, and how to write back.

```ts
interface EscalationResult {
  /** Atom ids the deep search decided were the right answer. */
  ids: string[]
  /** Or: content the deep search found that has no atom yet. */
  proposals?: AtomProposal[]
  /** Free-text provenance for the record. */
  via: string
}

type Escalator = (query: string, context: EscalationContext) => Promise<EscalationResult>
```

`src/escalation.ts` stays pure: it decides *whether* to escalate and computes the
writeback from a result handed to it. The async host function is wired in the
adapter, exactly like every other I/O boundary.

### The writeback, and its one hard problem

Given "the query that failed" and "the atom that should have won", the obvious
move is to add the query's terms as keywords. The obvious move is wrong in one
specific way: it will happily add stopwords, numbers, and whole phrases that
generalise badly, and after fifty escalations every atom matches everything.

So the writeback is **proposed, not applied**, and it is filtered:

- terms already covered by an existing keyword, stem, or prefix → dropped
- stopwords and bare years → dropped (the language profile already knows these)
- the proposal must **improve the eval** — run the suite with and without; if
  precision drops, the proposal is refused

That last rule is the oracle. A keyword addition that makes retrieval worse
cannot land, and we find out mechanically rather than by judgement.

**The close decision:** auto-apply vs. propose. Auto-apply is the whole appeal —
the system tunes itself while you sleep. But keywords are the highest-leverage
field in the contract; a bad addition degrades every future query. Gating on
"the eval must not regress" is what makes auto-apply defensible, so:
**auto-apply is allowed only when the eval improves and no `mustNotRetrieve`
case breaks.** Otherwise it becomes a proposal in the gap report.

### The record

```ts
interface EscalationRecord {
  query: string
  scope?: string
  bestScore: number       // what the cheap layer managed
  threshold: number
  resolvedIds: string[]
  via: string
  at: string
  writeback: { atomId: string, keywords: string[] } | null
  outcome: 'applied' | 'proposed' | 'refused-eval' | 'no-op'
}
```

Appended to `.memory-out/escalations.jsonl`. This file is the honest measure of
whether the cheap layer is any good: escalation rate over time is the metric,
and it should fall.

## Surfaces

**CLI**

```bash
amk escalations              # rate over time, most-escalated queries
amk escalations --pending    # writebacks proposed but not applied
amk escalations --apply <id> # apply one after review
```

**MCP** — `memory_search` gains `escalation` in its result:

```json
{ "scopeStatus": "no_match",
  "escalation": { "recommended": true, "reason": "nothing scored above 3",
                  "afterwards": "call memory_learn with what you found" } }
```

New tool `memory_learn`: the agent reports what its deep search found, the
server computes and gates the writeback. This is the agent-facing half of the
loop and the reason it works without the kit owning a search client.

**Library** — `shouldEscalate(result, config)`, `planWriteback(record, base)`,
`applyWriteback(...)`. All pure.

## UX / DX / AX

**User (UX).** Mostly invisible, and that is correct — the system quietly gets
better at finding things. The one visible artifact is `amk escalations`: a
falling line means the memory is learning its own vocabulary. If the line is
flat, something is wrong and the user should be able to see that in one command.

**Developer (DX).** One function to provide. The default is no escalation at all,
so nothing changes for anyone who does not want it. The temptation to make it
easy by shipping a default escalator (a web search, say) must be refused — that
would put a network client in a zero-dependency kit.

**Agent (AX).** This is where the design lives or dies. The flow is:

1. `memory_search` → `no_match` with `escalation.recommended: true`
2. the agent does whatever it is good at — reads files, searches, asks
3. `memory_learn` with the query and what it found

The `memory_search` result must *say* step 3, in the result, in plain language.
An agent that escalates and never reports back gives us the cost with none of the
learning, and it will do exactly that unless told otherwise in the payload it is
already reading.

Second AX rule: `memory_learn` must be cheap to call and safe to call wrongly.
If the agent reports something useless, the eval gate refuses it and says so.
Never punish a report.

## Tests

- [ ] `shouldEscalate` fires exactly on `no_match`, never on `match`
- [ ] a writeback that improves the eval is applied
- [ ] a writeback that degrades precision is refused, with the delta reported
- [ ] a writeback that breaks a `mustNotRetrieve` case is refused
- [ ] stopwords, bare years, and already-covered terms are filtered out
- [ ] proposing the same writeback twice is idempotent
- [ ] the escalation record round-trips through JSONL
- [ ] an escalation resolving to a *new* atom goes through `planApply` and the
      contract, like any other write
- [ ] parallel mode returns the cheap result when it matches, without waiting
- [ ] end to end: query misses → escalate → writeback → **the same query now
      matches**. This is the one that proves the whole release.

## Risks

**Keyword pollution.** The main risk, addressed by the eval gate — but the gate
only catches damage the eval can see. A memory with thin eval coverage will
accept writebacks that are merely useless. Mitigation: `amk escalations` reports
eval coverage alongside the escalation rate, so thin coverage is visible.

**Escalation as a crutch.** If escalation is cheap enough, nobody fixes the
keywords and every query pays deep-search cost forever. Mitigation: the rate is
the headline metric and it is supposed to fall. If it does not, that is the
finding.

**The agent never calls `memory_learn`.** Likely, unless the search result makes
it obvious. Mitigation is entirely in the payload wording, and it should be
tested by reading the actual result text, not just its shape.

## Done when

- [ ] the end-to-end test passes: a query that missed now matches
- [ ] `amk escalations` shows a rate over a seeded history
- [ ] `memory_learn` is exercised over the MCP server in a test
- [ ] the eval gate demonstrably refuses a harmful writeback
- [ ] `docs/ESCALATION.md` explains why no escalator ships with the kit

## Kill criteria

- If the eval gate refuses most writebacks, the signal is not as clean as this
  plan assumes. Keep the record (it is diagnostic), drop the automatic writeback,
  and make it a report a human reviews.
- If escalation rate does not fall over a month of real use, the writeback is
  not learning anything and this is expensive theatre. Say so and remove it.
