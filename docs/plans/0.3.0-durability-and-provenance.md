# 0.3.0 — Durability & provenance

**Contract 1.1.0** (additive) · Status: planned

## Goal

Make "what belongs in this memory at all" a machine-checkable property instead
of prose, and give knowledge that came from outside a way to expire.

## Why now

`VERDICT.md` argues a two-tier split: episodic memory stays with Anthropic,
curated memory comes here. Today that boundary lives in a paragraph. Nothing
stops an agent writing *"meeting Wednesday with X about Y"* as an atom, and
nothing will — until the thousandth thin atom makes the memory unmaintainable
and the whole thing gets abandoned. That is the single most likely way this
project fails in real use.

Provenance rides along because it is the same contract bump and the same review:
`research` knowledge without an expiry ages into the most confident and least
trustworthy part of the store.

## Contract impact

Four additive standard fields. Contract **1.0.0 → 1.1.0**. No atom valid under
1.0.0 becomes invalid; all four are optional.

| Field | Type | Class | Default |
|---|---|---|---|
| `durability` | string enum | standard | `stable` |
| `source` | string | standard | — |
| `retrievedAt` | string (ISO date) | standard | — |
| `validUntil` | string (ISO date) | standard | — |

### `durability`

```yaml
durability: fixed     # changes ~never. The user's name. A company's founding year.
durability: stable    # the default. Preferences, product facts, research findings.
durability: volatile  # "meeting Wednesday" — REFUSED on write.
```

`volatile` is not a value the kit stores. It is a value the kit **rejects**,
with a message naming where the content belongs instead. That is the entire
feature: one enum, one refusal, and the Tier-1/Tier-2 boundary stops being
advice.

**The close decision:** reject vs. quarantine. Quarantine is friendlier and will
silently become Tier 1 in disguise — a directory nobody empties, growing the
exact pile this project exists to avoid. Reject teaches the boundary at the only
moment anyone is paying attention. Rejecting.

**Severity:** `E_DURABILITY_VOLATILE`, an error. An unknown *value*
(`durability: seasonal`) warns per R4.1 and is treated as `stable`.

### `source`, `retrievedAt`, `validUntil`

```yaml
source: https://example.com/pricing
retrievedAt: "2026-08-30"
validUntil: "2026-11-30"
```

- `source` — where a claim came from. Absolute URL or a free string for
  offline provenance ("Slack thread with Anna, 2026-08-12").
- `retrievedAt` — when it was checked. Not when the atom was written.
- `validUntil` — after this date the atom is *suspect*, not deleted.

Nothing expires automatically. An expired atom keeps serving; it produces a gap
of kind `expiry`. Silent deletion of knowledge is the failure mode
`LIMITATIONS.md` exists to prevent, and an expired-but-present atom the user can
see is strictly better than an absent one they cannot.

**Dates as strings, quoted.** `retrievedAt: 2026-08-30` parses as three numbers
in most YAML; ours would take it as a string but a foreign L1 implementation
might not. The contract requires quotes and the validator warns without them
(`W_DATE_UNQUOTED`).

## Design

```
write ─→ parse ─→ validate ─→ durability gate ─→ store
                                    │
                                    └─ volatile → E_DURABILITY_VOLATILE
                                       "This looks like session knowledge.
                                        It belongs in your agent's working
                                        memory, not here. Nothing was written."
```

New gap kind `expiry`, produced by a detector that compares `validUntil` against
the clock. Joins the existing six.

**Where the clock lives.** `src/` is pure — no `Date.now()` anywhere in it, and
that is not negotiable, because it is what makes the round-trip and every test
deterministic. The expiry detector therefore takes `now` as a parameter and the
adapter supplies it. Same shape as every other detector.

## Surfaces

**CLI**

```bash
amk expiring [--within 30d]     # what goes stale soon, sorted by date
amk gaps                        # now includes expiry gaps
amk contract                    # shows the four new fields
```

**MCP** — `memory_contract` gains the fields automatically (it serialises
`FIELDS`). `memory_gaps` gains `kind: "expiry"`. No new tools.

**Memory tool** — a `create` with `durability: volatile` is refused with the
message above. This is where the feature earns its keep: the agent learns the
boundary from a tool result, in the turn where it tried to cross it.

**Library** — `checkExpiry(base, now)` → `GapObservation[]`, same shape as
`checkDrift`.

## UX / DX / AX

**User (UX).** They see `amk expiring` and a dated list. The point is that
staleness becomes visible *before* someone acts on a wrong number, not after.
One rule for the output: never show a naked date. `"2026-09-15 (in 16 days)"` —
relative time is what a human actually reasons with.

**Developer (DX).** Four optional fields; existing memories keep working with no
migration and no flag. The one thing a developer must learn is that `volatile`
is a refusal, and they learn it from the error message rather than the docs.
`amk validate` on an existing memory must stay silent about durability — a
sudden wall of "consider adding durability" on 200 atoms is how a minor version
gets skipped.

**Agent (AX).** Three things:

1. The refusal message must say *where the content belongs instead*. "Rejected"
   teaches nothing; "this is session knowledge, keep it in your working memory"
   teaches the boundary in one sentence.
2. `memory_contract` must carry the enum values *and* one example each. An agent
   choosing `durability` from the name alone will guess wrong on the middle case.
3. Expiry gaps must include the source URL, so a research agent can act without a
   second lookup.

## Tests

The oracle for durability is trivial and total: a `volatile` write either
reaches disk or it does not.

- [ ] `volatile` refused at `planApply`, at `memory_apply`, and through the
      memory-tool `create` / `str_replace` / `insert` paths
- [ ] the refusal message names the alternative
- [ ] unknown durability value warns and behaves as `stable` (R4.1)
- [ ] `durability` survives the round-trip, including through the bundle
- [ ] unquoted date warns, quoted date does not
- [ ] `checkExpiry` with an injected `now`: before, on, and after `validUntil`
- [ ] an expired atom is still retrieved — expiry is a gap, not a deletion
- [ ] expiry gap deduplicates by atom id and reopens on re-observation
- [ ] contract self-consistency: the four fields appear in `CONTRACT.md`,
      `FIELDS`, and are enforced by `schema.ts` (existing derivation test covers
      this automatically once the fields are declared)

## Risks

**The enum is too coarse.** Three values will not fit everyone. Mitigation: it
is a standard field with R4.1 semantics, so a fourth value warns rather than
breaks, and anyone needing finer control uses an extension field. Do not add
values speculatively.

**`volatile` becomes a fight.** An agent that keeps trying to write session
knowledge will keep getting refused, burning turns. Mitigation: the refusal
message is explicit about the alternative, and it is one line in the agent's
system prompt to avoid the whole class.

**Provenance theatre.** A `source` field that nobody fills, or fills with
"internal", is worse than no field because it looks like rigour. Mitigation: do
not warn when it is absent. It earns its place in `research` scopes (0.4.0),
where the audit can require it, and nowhere else.

## Kill criteria

- If the three-value enum cannot survive a week of real use without a fourth
  value being obviously needed, the model is wrong. Stop and rethink rather than
  adding values.
- If `volatile` refusals turn out to be rare in practice — agents simply do not
  try to write session knowledge here — then the gate is ceremony. Keep the
  fields, drop the refusal, and say so in `LIMITATIONS.md`.
