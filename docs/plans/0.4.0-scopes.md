# 0.4.0 — Scopes

**Contract 1.1.0** (no change) · Config: breaking · Status: planned

## Goal

Let one installation hold several memories with different natures — `personal`,
`business`, `research` — sharing one contract and one gap ledger, but with their
own review policy, their own eval set, and their own answer to *who closes a gap
here*.

## Why now

Three things collide once a memory serves more than one purpose:

- **Authority differs.** The user is the authority on their own preferences.
  Nobody is the authority on a research finding except the source.
- **Correction differs.** A wrong personal fact gets edited. A wrong research
  fact gets *re-fetched* — editing it by hand is how a citation becomes a lie.
- **A gap means different things.** `personal` → ask the user. `business` → ask
  the user. `research` → go and look it up.

That last row is the whole feature. Today every gap is routed the same way, so
`memory_close_gaps` asks a human about things a search agent should have
answered, and a research agent has no signal telling it what to go find.

## Contract impact

None. Scopes are configuration, not frontmatter.

**The close decision:** `scope` as a core field vs. scopes as configured roots.
A field is tempting — one directory, one loader, less machinery. It is wrong,
because the three differ in *policy*, and policy in frontmatter is a value the
author can set to whatever they like. A `research` atom that declares itself
`personal` to skip the provenance requirement is a hole in the design. Roots
with config keep the policy above the content.

## Design

```json
{
  "scopes": {
    "personal": {
      "root": "memory/personal",
      "gapRoute": "user",
      "durabilityDefault": "stable",
      "retrieval": { "categories": ["preferences", "profile"] }
    },
    "business": {
      "root": "memory/business",
      "gapRoute": "user",
      "retrieval": { "categories": ["product", "pricing", "goals"] }
    },
    "research": {
      "root": "memory/research",
      "gapRoute": "research",
      "requireProvenance": true,
      "retrieval": { "categories": ["market", "technical", "regulatory"] }
    }
  },
  "gapLedger": ".memory-out/gaps.jsonl"
}
```

Single-root configs keep working: absent `scopes`, the existing `root` becomes
an implicit scope named `default`. No migration, no flag.

### One ledger, not three

Gaps gain a `scope` field. **One ledger** — because "what does this whole system
not know" must stay answerable in one place, and that was the original point of
the ledger. Three ledgers means three files to merge before anyone can answer it,
and nobody will.

`gapRoute` then decides who acts:

| Route | Closed by | Mechanism |
|---|---|---|
| `user` | a human | MRTR elicitation, as today |
| `research` | an agent, **citing a source** | write with `source` + `retrievedAt` |
| `manual` | a human, out of band | no automation |

### The research route and the human gate

This is the thinnest part of the design and `IDEAS.md` §7 flags it as an open
question. Decision: **a research gap may be closed by an agent, but only by a
write that carries `source` and `retrievedAt`.** The source is then the oracle,
and the provenance is checkable after the fact.

This is not a hole in the human gate — it is the gate moved to a different place.
For personal and business knowledge the human *is* the authority, so they must
answer. For research the human is usually not the authority, and requiring their
approval buys ceremony rather than correctness. What it does require is that
`requireProvenance: true` makes a research write without `source` a hard refusal,
so the escape hatch cannot be used silently.

### Retrieval across scopes

`searchMemory` gains an optional `scopes: string[]`. Default: all. Each scope is
loaded as its own base; results merge and re-sort by score.

**The cost, stated:** N scopes means N token caches in RAM and N passes per
query. At three scopes and a few hundred atoms this is microseconds and a few
megabytes. It does not need optimising and it must not be optimised
speculatively — a shared index across scopes would reintroduce exactly the
coupling that scopes exist to prevent.

## Surfaces

**CLI** — every command takes `--scope`, defaulting to all:

```bash
amk validate --scope research
amk gaps --scope personal
amk compile --scope personal      # one page the user can actually review
amk doctor                        # all scopes, grouped
```

**MCP**

- `memory_scope` groups by scope, then category
- `memory_search` takes `scopes?: string[]`
- `memory_gaps` takes `scope?` and returns `gapRoute` per gap
- `memory_close_gaps` filters to `gapRoute: "user"` — the change that makes it
  stop asking humans about research

**Memory tool** — `/memories/<scope>/...`. The first path segment is the scope.
A write to an unknown scope is refused with the list of valid ones.

## UX / DX / AX

**User (UX).** `amk compile --scope personal` produces one reviewable page of
everything the system believes about them — the concrete answer to "what does it
know about me", and it is editable and re-importable. That page is the most
user-facing artifact this project will ever produce and it should read like
prose, not a data dump.

`research` gets the same command but the framing is different: the user is not
correcting it, they are auditing sources. Different header text, same mechanism.

**Developer (DX).** Config gains one key. The old shape keeps working. The
failure everyone will hit is a typo in a scope name, so: an unknown `--scope`
lists the valid ones and exits non-zero. Never silently search everything.

**Agent (AX).** The gap's route tells the agent whether this is its job. A
research agent polls `memory_gaps --route research`, does the lookup, writes with
provenance, and the gap closes — no human in that loop, by design, with the
source recorded so the decision is auditable.

`memory_scope` output must lead with what each scope is *for*, in one line. An
agent choosing between three scopes by name alone will put product facts in
`research` about a third of the time.

## Risks

**Scope sprawl.** Nothing stops someone defining eleven scopes, at which point
routing is noise and every search is eleven passes. Mitigation: document three
as the intended shape, warn above five, refuse nothing.

**Cross-scope edges.** `related[]` currently resolves within one base. Do we
allow `personal.x` → `research.y`? **No, in 0.4.0.** Cross-scope edges mean
loading every scope to validate any scope, which breaks per-scope degraded mode
and independent loading. Revisit only with a concrete case; a link field can
carry the reference in the meantime.

**The research route is the weak point.** If an agent can close research gaps by
citing a source, an agent that fabricates a plausible URL closes gaps with
nothing behind them. Mitigation: `source` must be syntactically checkable, the
audit pass (0.6.0) can re-fetch and compare, and — honestly — this is a residual
risk that needs stating in `LIMITATIONS.md` rather than engineering away.

## Kill criteria

- If three scopes cannot be kept distinct in practice — if everything lands in
  one — the split is imaginary. Ship a `category` convention instead and delete
  the machinery.
- If the research route produces more unverifiable atoms than it closes real
  gaps, revoke it: research gaps go back to `gapRoute: user` and an agent may
  only propose.
